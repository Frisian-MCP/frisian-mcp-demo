frisian-mcp demo

Stock Nautobot, with one settings file swapped in. Everything below is what that file configures.

Every credential on this page is published on purpose. They are fixed constants, identical in every build, and they are not secrets — the demo's safety property is that it binds to 127.0.0.1, not that anything here is hidden. Do not reuse any of them anywhere, and do not bind this stack to 0.0.0.0.

Log in

Web UI at http://127.0.0.1:8080 — password frisian-demo-public-password for all three accounts.

If your browser autofills a saved Nautobot password, the login will fail and the field is blanked so you cannot see what was sent. Paste the password, or use a private window.

The three identities

Three identities, three doors, three tier ceilings. The door and the account's own permissions are independent controls — which is the thing this demo exists to show.

accountMCP doortier ceilingDjango permissions
demo-readonly/mcp/read-onlyread view on the scoped estate
demo-netops/mcp/read-writeread_write view on all scoped apps; write on dcim and ipam only
demo-admin/mcp/adminadmin superuser — bypasses per-object permissions entirely

MCP tokens

demo-readonly   Bearer frisian-demo-readonly-token-public-do-not-reuse
demo-netops     Bearer frisian-demo-netops-token-public-do-not-reuse
demo-admin      Bearer frisian-demo-admin-token-public-do-not-reuse

Each token is only accepted at its own door. A door is a mount point, not a filter on the token — presenting the read-only token at /mcp/admin is refused, and /mcp/ itself is 404, so the doors never collapse onto a default mount.

demo-netops is the interesting one. Its door permits the write tier across all twelve scoped resource groups. Its own Django permissions permit writes to two of them.

So it is refused a write its door plainly allows — and that refusal is the feature. If both controls were set to the same thing, you could not tell which one was doing the work.

Two things worth trying first

1. Do not compare tools/list lengths on the scoped doors. It is the intuitive move and it proves nothing — both return 12 tools with identical names. Two filters run in series: the route's allow-list fixes the candidate set, then permission-aware discovery filters within it. On the scoped doors the first filter has already removed almost everything the two identities differ on.

The same door, asked by demo-admin, returns 13:

/mcp/read-only   demo-readonly   12
/mcp/read-write  demo-netops     12
/mcp/read-only   demo-admin      13    <- load_balancers

load_balancers is on that door's allow-list, so it is mounted for everyone — hidden from identities that cannot use it, not absent. Invoking it proves the difference, because a refusal is not the same answer as a missing route:

demo-readonly   403  "You do not have permission to use 'loadbalancerpool'/'list'"
demo-admin      200

2. Ask a dispatcher what it will let you do. Send action: "help" to dcim and then to dns as demo-netops. Same door, same token, two different answers — that is where the per-identity difference shows plainly.

Resetting

The database runs on a tmpfs, so the estate is restored on every start — including docker compose restart. Break anything you like; a restart puts it back, and getting back to a known-good demo never takes more than that.

The settings file driving all of this is nautobot/config/nautobot_config.py in the repository, mounted over Nautobot's own. Read it, change it, docker compose restart.
